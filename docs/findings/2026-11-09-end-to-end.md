# 実機での一周 (AWS S3 + GitHub Pages + Bark) と、そこで判明したこと

- Date: 2026-11-09
- 対象: 実装 ③a / ③b (helper のストア連携、`setup` / `add` / `list` / `del`、承認 / 登録ページ `https://pam-passkey.github.io/`)。ストアは AWS S3 (ap-northeast-1、`s3:PutObject` / `GetObject` / `DeleteObject` と `PutBucketCORS` / `PutLifecycleConfiguration` だけの IAM ユーザ)、通知は `send_command` から Bark
- 環境: macOS 26.5.2、`/etc/pam.d/sudo_local` は `auth sufficient /usr/local/lib/pam/pam_passkey.so` の 1 行だけ (pam_tid は外した)

## 判明した事実

- iPhone からの承認が通る: Mac の前に居ない状態で `sudo` (`just install`) を実行し、Bark の通知の URL を iPhone で開いて passkey で承認すると sudo が通る (kawaz 2026-11-09、リモート作業中。Touch ID ダイアログは Mac の画面に出たままで、承認後に閉じる)
- 承認の一周が通る: `sudo` → Touch ID ダイアログと helper が並走 → helper が PAM_USER の login keychain から設定と登録を読み、request を PUT、承認 URL を `send_command` (Bark) に渡す → (a) Touch ID で通すと PAM_SUCCESS、helper は result `pass` を PUT して request / assertion を DELETE、(b) 「詳細を確認」→ ブラウザの承認ページで passkey 署名 → sudo が通る
- `add` の一周が通る: 本人確認 → 登録 URL → ページで passkey 作成 → credential を PUT → `add` が検証して login keychain に保存 → `list` に出る
- AWS S3 では `PutBucketCors` / `PutBucketLifecycleConfiguration` が通り、`If-None-Match: *` 付きの 2 回目 PUT は 412 (`put_once: yes`)
- AWS S3 は `s3:ListBucket` の無い鍵では未存在オブジェクトの GET に 404 でなく 403 を返す (MinIO は 404)。poll は 403 / 404 を「まだ無い」として扱う
- System Keychain の既存項目の更新で `kSecAttrAccess` (ACL) を付け直すと、root でも、ユーザ操作を禁止していても、項目ごとに管理者認証ダイアログが出る。データだけの更新なら出ない。delete → add でも出る。新規作成では出ない
- login keychain の項目は、ユーザ権限で作成も更新も無ダイアログ (ACL は作成時だけ付ける)
- LAContext は、呼び出し元の session に graphic access が無い系統 (launchd → ccmsg daemon → hyoui → claude → シェル) からでも出せる: ユーザ権限の直接実行、root から `seteuid(user)`、root から PAM_USER に永久降格した子、の 3 通りとも成功。事前に session の属性で切る必要は無く、試して失敗したら不可にすればよい
- 画面ロック中 (リモート作業中) は `evaluatePolicy` が即座に -4 (`LAErrorSystemCancel`) を返し、ダイアログは出ない。remote のみになり、承認が無ければ 90 秒で期限切れ → `PAM_AUTH_ERR` → tty 無しの sudo は「a terminal is required」で終わる
- `canEvaluatePolicy` が -8 (`LAErrorBiometryLockout`) の間は Touch ID が一切出ない。ロック画面でパスワードを入れると解除される。tty 無しで Touch ID も remote も使えないと、sudo は即座に `a password is required` で終わる
- 「詳細を確認」の後に出し直したダイアログは、ブラウザを activate した直後に前面に出て邪魔になる (順序を入れ替えても OS がダイアログを出すタイミングは制御できない)
- 同時に走る複数の sudo のダイアログは独立に出て同じ座標に重なる
- `cargo test` から keychain を触るテストは、使い捨て keychain でも検索リストに入るとダイアログの見た目が本物と区別できず、ユーザを混乱させる。keychain を触るテストは `#[ignore]` にして手元でだけ回す
- Developer ID 署名の `pam-passkey` は、ユーザ権限で System Keychain の設定項目 (secret 含む) を無ダイアログで読める (ACL に自分が入っているため)

## 実用的な示唆

- 設定 (page_url / store / send_command) はユーザの login keychain に置く (ユーザ単位、sudo 不要、ダイアログ無し)。System Keychain に置くのは署名鍵と検証鍵だけで、初回に作って以後触らない
- Keychain の既存項目の更新では ACL を付け直さない
- Touch ID の可否は事前判定せず、評価を試して失敗 (-4 / -5 / -6 / -7 / -8 / -1004) なら remote のみにする
- Touch ID の評価は helper の降格した子からでも出せるので、PAM 内の seteuid を無くす改修が可能
- 「詳細を確認」の後の出し直しは、ページ側のボタンで利用者が要求した時だけにする方がよい
- unified logging (`subsystem == "jp.kawaz.pam-passkey"`) が無いと実機の切り分けができない
